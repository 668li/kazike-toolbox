# PR 卡顿审计

> 来源：用户投稿（2026-11-19）· 原始表述：「全面分析最近XX天里的所有的PR，找出最慢的那几个，看看有没有导致卡顿、可以优化的地方。」
> 解决的问题：交付越来越慢，但说不清慢在哪个环节。

## 什么时候用

感觉「最近什么都推不动」，或者想知道 PR 周期为什么变长。

## Prompt

```
请分析【仓库】最近【XX 天】的 PR 数据。

先找出耗时最长的 PR，把时间拆开：等待 review、等待 CI、反复修改、讨论僵持、依赖阻塞、范围膨胀，还是根本没人管。对最慢的 5 个逐个给出：耗时分解、根因、可优化的动作。

然后回答：
1. 慢是普遍现象，还是集中在少数 PR？
2. 有没有固定的卡点（某类改动、某个检查、某个环节）？
3. 哪些环节可以自动化或并行？
4. 哪些慢是合理的（大改动本来就需要时间）？

最后给出 3 个能系统性缩短周期的改动，估算各自能省多少时间。没有数据的地方标「无数据」，不要编。
```

## 执行要点

- 先确认**数据源可用**（`gh pr list`、仓库 API、或导出记录）；拿不到就说拿不到。
- 区分**等待时间**和**工作时间**：等 review 三天和改代码三天是两种问题。
- 不要把所有慢都归因于 review；先看分布再下结论。
- 建议落到**流程或自动化**，不要写成「大家要更积极」。
- 估算要写假设，没把握就给区间。
