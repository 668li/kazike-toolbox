# 二阶三阶影响推演

> 来源：用户投稿（2026-11-19）· 原始表述：「不要只考虑这个改动产生的直接效果。继续推演它的二阶、三阶影响，尤其关注对其他模块、用户行为、系统复杂度和长期维护成本的潜在影响。」
> 解决的问题：改动本身有效，却把别处搞坏了，或者一年后变成新的技术债。

## 什么时候用

要动一个牵涉面不小的东西：改架构、改流程、改产品机制、改团队约定。直接效果已经看清，需要看连锁反应。

## Prompt

```
我准备做的改动是：【填写改动内容、涉及模块、预期收益和已知约束】。

不要只分析直接效果。请分三层推演：
1. 一阶：这次改动直接改变了什么。
2. 二阶：对相邻模块、上下游流程、用户行为、协作方式的反作用。
3. 三阶：对系统复杂度、长期维护成本、团队习惯、可逆性的影响。

每条影响标注：发生概率（高/中/低）、方向（正/负）、可观测信号、发生后怎么补救。

最后列出：1. 最容易被忽略的 3 条连锁反应；2. 最可能让这次改动在 12 个月后变成负债的那一条；3. 一个能提前暴露风险的检查点（什么时候看什么指标）。
```

## 执行要点

- **只写真实链条**，每条都要能说出「因为 A 所以 B 所以 C」。列 20 条泛泛而谈等于没做。
- **区分事实与推测**：有数据支撑的写事实，其余标推断。
- 必须给**观测信号**，否则影响无法验证。
- 重点盯一个账：**改动省下的成本，有没有被新增的维护成本吃回去**。
- 三阶不要写成灾难幻想，给概率和补救措施。
