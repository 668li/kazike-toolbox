# 新人认知成本审计

> 来源：用户投稿（2026-11-19）· 原始表述：「假设明天有一个完全不了解项目、但是能力很强的工程师来接手。请评估他理解整个项目需要付出的认知成本，找出那些命名混乱、抽象过度、职责不清晰、需要大量上下文才能理解的代码，并提出简化方案。」
> 解决的问题：只有老人敢改，新人上手要几个月，团队被少数人卡住。

## 什么时候用

项目交接、团队扩张、或者感觉「代码只有作者本人看得懂」时。

## Prompt

```
假设明天有一位能力很强、但完全不了解这个项目的新工程师接手：【项目路径/范围】。

请评估他的认知成本：
1. 他要独立完成一次典型改动，需要读哪些文件、花多久？
2. 哪些命名会让人误解？列出「现名 → 它实际是什么 → 建议名」。
3. 哪些地方抽象过度？比如只有一层调用却包了三层、为了「将来可能」预留的扩展点。
4. 哪些文件/模块职责不清晰，一个地方干了几件事？
5. 哪些地方必须问老人才敢改？这些隐性知识是什么？

按「理解成本 × 出错概率」排序，给出前 5 个最该简化的点。每个点写清：具体怎么改、改完新人能省什么、不改的代价是什么。不要用「加注释/写文档」当万能答案，优先动结构。
```

## 执行要点

- 必须**真读代码**，按真实调用链评估，不能按目录名猜。
- 命名问题要列**具体清单**，不要只说「命名不规范」。
- 简化优先做**减法**：删抽象、合并职责、去掉死扩展点；加文档是最后手段。
- 区分「**业务本身复杂**」和「**历史堆出来的复杂**」，只有后者该简化。
- 「新人要多久」给区间和依据（文件数、入口数、必须问人的点），不要拍一个数字。
