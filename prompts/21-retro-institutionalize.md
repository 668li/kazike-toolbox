# 复盘与制度化

> 来源：用户投稿（2026-11-19）· 原始表述：「全面复盘最近XX时间的 Bug、返工、回滚和重复修改。不要只统计发生了什么，要分析这些问题背后有没有共同的根因。把能够预防的共性问题沉淀成项目规则、自动化或者Skill，避免我们反复支付同样的成本。」
> 解决的问题：同一个坑反复踩，每次都修，但从不防。

## 什么时候用

一段时间内反复返工、回滚、修同类 Bug，或者项目刚经历一次事故。

## Prompt

```
请复盘【项目/仓库】最近【XX 时间】的 Bug、返工、回滚和重复修改。

不要只统计发生了什么。请：
1. 按现象聚类：哪些问题其实是同一类？
2. 对每一类做根因分析，连问 5 个为什么，直到找到可干预的机制层原因（流程、约束、缺失的检查、错误的心智模型），而不是停在「某人粗心」。
3. 区分偶发问题和结构性问题。
4. 找出跨类别的共同根因（如果有）。
5. 把可预防的共性问题转成具体产出：一条项目规则、一个自动化检查、一个 Skill、或一个模板。每个产出写清：拦截什么问题、放在哪个环节、误报怎么办、谁来维护。

最后按「复发频率 × 单次代价」排序，给出最该先做的 3 件事。只做统计、不给拦截机制的复盘不算完成。
```

## 执行要点

- 不许停在个人归因。「某人粗心」不是根因，缺少什么检查/约束才是。
- 每个根因必须能对应一个**拦截动作**，否则不算分析完。
- 规则要**少而硬**：一条能自动执行的检查，胜过十条口号。
- 区分**一次性事故**和**系统性风险**，别把偶发问题制度化成繁文缛节。
- 产出必须可执行：写清放在哪个环节、谁维护、误报怎么处理。
